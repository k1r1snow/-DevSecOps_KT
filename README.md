# Сервис управления задачами

Микросервисное веб-приложение для управления задачами с сохранением данных в PostgreSQL, подсчётом аналитики и журналом уведомлений.

## Состав проекта
* **`task-api` (порт 8080)** — главный сервис (CRUD задач, веб-интерфейс и `/health`).
* **`analytics-service` (порт 8081)** — сервис подсчёта созданных и изменённых задач.
* **`notification-service` (порт 8082)** — сервис хранения истории уведомлений.
* **`db` (порт 5432)** — база данных PostgreSQL 16 (с сохранением данных в volume `db_data`).
## Архитектура системы (C4 Model)

### 1. Описание системы
**Микросервисная система управления задачами (`Task Management System`)** предназначена для пользователей и проектных команд, которым необходимо вести учёт рабочих поручений (создание, просмотр, редактирование, удаление) с автоматическим подсчётом статистики активности и журналированием системных событий.

### 2. Основной пользовательский сценарий
1. Пользователь открывает веб-интерфейс или отправляет REST-запрос на создание/получение списка задач.
2. Запрос поступает на единую точку входа **API Gateway / Load Balancer (Nginx)**, который маршрутизирует трафик в главный сервис **`task-api`**.
3. При чтении списка задач (`GET /tasks`) сервис проверяет наличие актуальных данных в кэше **Redis**; при отсутствии данных в кэше выполняет запрос в реляционную БД **PostgreSQL** и обновляет кэш.
4. При создании или изменении задачи (`POST /tasks`, `PUT /tasks/{id}`) **`task-api`** сохраняет запись в **PostgreSQL**, сбрасывает устаревший кэш в **Redis** и отправляет HTTP-уведомления в микросервисы аналитики (**`analytics-service`**) и уведомлений (**`notification-service`**).

#### C4 Level 1 — Context (Контекст)
Показывает систему как единый «чёрный ящик» и её взаимодействие с внешним окружением:
* **Client (Пользователь):** взаимодействует с системой через браузер (Web GUI) или HTTP-клиент (`curl` / Postman) по протоколу HTTP/REST.
* **Task Management System:** программная система для управления задачами, сбора аналитики и ведения лога уведомлений.

#### C4 Level 2 — Container (Контейнеры)
Описывает отдельно развёртываемые модули, хранилища данных и сетевое взаимодействие между ними:
* **API Gateway / Load Balancer (`Nginx`, порт `80`):** единая точка входа в систему на уровне L7. Скрывает внутреннюю сеть контейнеров, маршрутизирует запросы к микросервисам и распределяет нагрузку (Round Robin) между репликами `task-api`.
* **`task-api` (`Java / Spring Boot`, порт `8080`):** главный бэкенд-сервис. Реализует CRUD-операции над задачами, отдаёт веб-интерфейс и координирует вызовы вспомогательных сервисов.
* **`PostgreSQL` (`postgres:16`, порт `5432`):** основная реляционная база данных для персистентного хранения таблицы задач (`tasks`) с использованием постоянного тома Docker (`db_data`).
* **`Redis Cache` (порт `6379`):** распределённое in-memory хранилище для кэширования частых запросов на чтение списка задач.
* **`analytics-service` (`Java / Spring Boot`, порт `8081`):** микросервис подсчёта общего количества операций над задачами.
* **`notification-service` (`Java / Spring Boot`, порт `8082`):** микросервис формирования и хранения журнала уведомлений о действиях в системе.

#### C4 Level 3 — Component (Внутренние компоненты `task-api`)
Детализирует внутреннее устройство главного сервиса `task-api`:
* **`TaskController` (`@RestController`):** принимает входящие HTTP-запросы от шлюза (`/tasks`, `/health`, `/container-id`) и возвращает JSON-ответы.
* **`TaskService` (`@Service`):** содержит бизнес-логику обработки задач, управляет логикой кэширования и координирует вызовы репозитория и внешних сервисов.
* **`TaskRepository` (`Spring Data JPA`):** слой доступа к данным, выполняющий SQL-запросы к базе данных PostgreSQL через Hibernate.
* **`RestTemplate Client`:** HTTP-клиент для синхронной отправки событий в `analytics-service` и `notification-service` по внутренней сети Docker.

### 4. Обоснование выбора компонентов
* **Почему выбран API Gateway / Load Balancer (Nginx):** обеспечивает единую входную точку для клиента, изолирует внутренние порты микросервисов от прямого внешнего доступа и позволяет горизонтально масштабировать главный сервис (`task-api`) с равномерным распределением трафика.
* **Почему выбрана PostgreSQL:** промышленная реляционная СУБД, гарантирующая надёжное хранение структурированных данных (ACID-транзакции), целостность записей и сохранность информации между перезапусками контейнеров за счёт Docker Volume `db_data`.
* **Почему выбран дополнительный компонент Redis Cache:** в системе управления задачами операции чтения списка задач (`GET /tasks`) выполняются значительно чаще операций записи. Использование in-memory кэша Redis позволяет мгновенно отдавать часто запрашиваемые данные из оперативной памяти и существенно снижать нагрузку на основную базу данных PostgreSQL при росте числа пользователей.
